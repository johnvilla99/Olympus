# Status

This research note tests the early product and category hypotheses captured in ACR-003 and the Brainstorms session that preceded it.

It is **evidence and analysis, not a decision**.

The market is changing quickly. Vendor capabilities described here reflect publicly available information reviewed on **2026-08-15** and should be revalidated before future product, investment, or positioning decisions.

---

# Research Question

The central question is:

> **Is "Project Intelligence" an open and defensible product position for Olympus, or are existing products already solving the same problem?**

Secondary questions:

- Is automated documentation stewardship differentiated?
- Are cross-tool knowledge graphs already common?
- Are engineering teams already buying "intelligence" platforms?
- Where does Olympus overlap existing vendors?
- What potential differentiation remains credible?
- Which assumptions from the Brainstorms session are unsupported?

---

# Executive Finding

The strongest conclusion from this research is:

> **The market opportunity may be real, but the claim that Olympus creates a wholly new category is not currently supported.**

Several adjacent categories are already active:

- Engineering Intelligence
- Engineering Management / Developer Productivity Intelligence
- Enterprise Search and Enterprise Knowledge Graphs
- AI-native Engineering Knowledge Bases
- Continuous Documentation
- Code Intelligence
- Agent Context / MCP knowledge layers

Multiple vendors already connect code, tickets, conversations, and documentation; build knowledge or teamwork graphs; feed context to AI agents; answer engineering questions; detect documentation drift; or automate documentation updates.

The market gap, if Olympus has one, is therefore **not simply "connect project tools and use AI to keep docs current."**

A stronger candidate differentiation is:

> **governed project knowledge + explicit authority + decision/lesson lifecycle + change impact + judgment across project history**

That remains a hypothesis and requires customer validation.

---

# Hypothesis 1: "Nobody Is Doing This"

## Assessment

**Rejected.**

There are several credible overlapping products and platforms.

The overlap varies by vendor, but major elements of the Olympus thesis already exist in-market:

- code + docs + ticket + conversation context
- knowledge graphs
- connected enterprise graphs
- agent context
- automatic documentation maintenance
- project and engineering insights
- human-reviewed agent actions

The competitive question is therefore not whether anyone is doing something similar.

The question is:

> **Which parts of the Olympus system are meaningfully different, valuable, and difficult to reproduce?**

# Competitive Landscape

## 1. Falconer

**Position observed:** AI-native engineering knowledge platform.

Falconer publicly describes a knowledge base that connects engineering knowledge, integrates with coding agents through MCP, supports read/write agent access, and detects drift between code and documentation.

Relevant overlap with Olympus:

- engineering knowledge layer
- code/document context
- living documentation
- knowledge graph language
- Cursor / coding-agent integration
- agent writes back into the knowledge base
- documentation drift detection

Why it matters:

Falconer is currently one of the closest competitors to the original **Documentation Steward** wedge. This significantly weakens any differentiation claim based only on "AI keeps engineering documentation current."

Potential Olympus distinction:

Falconer's public positioning emphasizes accurate engineering knowledge and agent context. Olympus could potentially differentiate through governed authority, explicit decision records, promotion state, lessons learned, provenance, conflict handling, and portfolio-wide judgment.

**Research source:** Falconer product and MCP documentation, reviewed 2026-08-15.

---

## 2. Unblocked

**Position observed:** application and engineering knowledge/context layer.

Unblocked augments source code with context from systems such as GitHub, Slack, Confluence, Linear, Jira, and other engineering sources, then answers questions about the application across web, messaging, and IDE experiences.

Relevant overlap with Olympus:

- code as a primary knowledge source
- cross-tool contextualization
- engineering questions answered from multiple systems
- project/application understanding beyond documents
- technical institutional knowledge

Why it matters:

Unblocked demonstrates that the concept "understand the project/application by combining code with surrounding context" is already a commercial product direction.

Potential Olympus distinction:

Olympus may be broader than application Q&A if it treats decisions, authority, governance, lessons, product context, and cross-project memory as first-class governed objects rather than supporting context.

**Research source:** Unblocked official documentation, reviewed 2026-08-15.

---

## 3. Atlassian Teamwork Graph + Rovo

**Position observed:** unified organizational work graph and agent context layer across Atlassian and third-party tools.

Atlassian's Teamwork Graph represents work objects such as Jira work items, Confluence pages, Slack messages, Google Drive files, and GitHub pull requests and connects relationships among them. Rovo and MCP capabilities can query this graph and use it as agent context.

Relevant overlap with Olympus:

- cross-tool graph
- projects, work, knowledge, and people connected
- GitHub + Jira + Confluence + third-party context
- agent reasoning over connected work data
- dashboards and contextual insights

Why it matters:

This is a direct challenge to the idea that "the graph" or "the intelligence layer above tools" is itself unique.

Atlassian already describes Teamwork Graph as a unified data/context layer connecting teams, work, knowledge, goals, and applications.

Potential Olympus distinction:

Olympus would need to emphasize **governed meaning**, not merely connected data: status, authority, provenance, approved decisions, supersession, lessons, continuity, and explicit human approval semantics.

**Research source:** Atlassian Teamwork Graph and Rovo documentation, reviewed 2026-08-15.

---

## 4. Glean

**Position observed:** enterprise search, enterprise graph, and agent platform.

Glean's Knowledge/Enterprise Graph connects content, people, activity, projects, and organizational entities across many enterprise systems. Glean also provides agent actions capable of updating systems such as Jira, GitHub, and Confluence while respecting permissions.

Relevant overlap with Olympus:

- enterprise graph
- context across many systems
- relationship-aware retrieval
- agents acting on enterprise knowledge
- keeping knowledge/work systems synchronized
- enterprise-scale organizational intelligence

Why it matters:

Glean demonstrates that "AI understands relationships across enterprise tools" is an established direction, not a greenfield category.

Potential Olympus distinction:

Glean is broad enterprise context infrastructure. Olympus could potentially be more opinionated about project knowledge governance and lifecycle: approved vs exploratory, decisions vs observations, authoritative vs advisory, supersession, lessons, and project-specific judgment.

**Research source:** Glean Knowledge Graph / Enterprise Graph and Agents material, reviewed 2026-08-15.

---

## 5. Swimm

**Position observed:** continuous code documentation.

Swimm has long promoted Continuous Documentation: code-linked documentation that is checked against code changes and can flag documentation that is likely out of date.

Relevant overlap with Olympus:

- code change triggers documentation integrity checks
- documentation drift detection
- continuous maintenance of technical knowledge
- documentation integrated into development workflow

Why it matters:

The core Documentation Steward problem predates the current Olympus concept and is already an explicit category/problem addressed by vendors.

Potential Olympus distinction:

Olympus should not compete merely on maintaining code documentation. Its stronger thesis is that a change may invalidate not only docs but decisions, requirements, standards, lessons, project assumptions, and cross-project knowledge.

**Research source:** Swimm Continuous Documentation material, reviewed 2026-08-15.

---

## 6. Red Hat Code-to-Docs Pattern

**Position observed:** open-source AI workflow for code-diff-to-documentation pull requests.

Red Hat published a workflow in 2026 where a GitHub Action analyzes a code diff, identifies documentation likely to require change, lets a reviewer choose proposed updates, and then creates a documentation PR. The same pattern can compare code changes against Jira-linked specifications.

Relevant overlap with Olympus:

- PR-triggered documentation analysis
- code diff -> affected docs
- human review
- generated docs PR
- specification-versus-code traceability

Why it matters:

This is extremely close to the narrow MVP flow proposed in the Brainstorms session.

The workflow therefore should not be treated as product differentiation by itself.

Potential Olympus distinction:

Use the same event-driven pattern, but reason over **governed Knowledge Assets**, not only documentation files.

**Research source:** Red Hat Developer, "AI-powered documentation updates: From code diff to docs PR in one comment," 2026.

---

## 7. GitHub Agentic Workflows

**Position observed:** repository-native autonomous workflows with safe outputs and human review.

GitHub has published examples of agentic workflows that generate cross-repository documentation pull requests after product changes, route them to appropriate reviewers, and avoid autonomous merge.

Relevant overlap with Olympus:

- repository events as triggers
- draft documentation PRs
- human approval boundary
- safe agent outputs
- cross-repository automation

Why it matters:

The enabling infrastructure for the Documentation Steward may increasingly become a commodity capability of development platforms.

Potential Olympus distinction:

Olympus should own **the reasoning policy and governed project model**, not rely on workflow orchestration itself as the moat.

**Research source:** GitHub Blog, "Automating cross-repo documentation with GitHub Agentic Workflows," 2026.

---

## 8. Engineering Intelligence Platforms (LinearB, Jellyfish and peers)

**Position observed:** management intelligence over software delivery, productivity, allocation, AI impact, and business alignment.

Engineering Intelligence is already an active market term. Platforms such as LinearB and Jellyfish aggregate engineering signals and present management-facing analysis on delivery, investment, productivity, alignment, and AI impact.

Relevant overlap with Olympus:

- executive/leadership buyer
- intelligence rather than raw project tracking
- dashboards
- risk and performance insight
- cross-system engineering data

Why it matters:

"Project Intelligence" may sound adjacent to or overlapping with an already-established Engineering Intelligence market. Olympus should not assume the word "intelligence" creates an uncontested category.

Potential Olympus distinction:

Engineering Intelligence generally emphasizes metrics and delivery behavior. Olympus could potentially emphasize **project meaning, decisions, governed knowledge, historical rationale, and institutional memory**.

**Research sources:** LinearB and Jellyfish official materials, reviewed 2026-08-15.

# Hypothesis 2: Documentation Steward Is the Product

## Assessment

**Rejected as a long-term differentiation claim; retained as a possible wedge.**

Automated documentation maintenance is already being addressed by:

- Falconer
- Swimm
- Red Hat Code-to-Docs
- GitHub agentic workflows
- broader agent platforms capable of GitHub/Confluence actions

The workflow may still be valuable as a first Olympus experiment because it is:

- visible
- testable
- event-driven
- auditable
- easy to demonstrate
- connected to an existing pain point

But the experiment should test a larger proposition:

> Can Olympus identify **governed knowledge impact**, not merely missing documentation edits?

# Hypothesis 3: The Knowledge Graph Is the Product

## Assessment

**Rejected.**

Knowledge and teamwork graphs are already foundational to products from Glean, Atlassian, Falconer, and others.

This reinforces the warning already captured in the Brainstorms session:

> the graph is infrastructure, not the customer value.

Olympus should not lead with graph technology unless a future implementation requires it.

The differentiating question is what Olympus **knows about the relationships** and how that changes judgment.

A relationship such as:

```text
PR-482 -> modifies -> service/auth.ts
```

is useful.

An Olympus-style governed relationship could be more consequential:

```text
PR-482
  potentially_invalidates -> ADR-014
  conflicts_with -> PDR-021
  requires_review_by -> Product Owner
  affects -> Project B
```

The value is not the edge. The value is the governed semantics and the action they enable.

# Hypothesis 4: "Project Intelligence" Is a New Category

## Assessment

**Unproven and currently weak.**

Reasons:

1. **Engineering Intelligence** is already a recognized and crowded positioning space.
2. Atlassian and Glean already describe graph-based intelligence/context layers across work and knowledge.
3. AI engineering knowledge vendors describe living knowledge bases and company/application brains.
4. "Project Intelligence" may be interpreted as project-management analytics rather than governed project understanding.

Therefore:

> Olympus should treat "Project Intelligence" as a **working product thesis**, not a category claim.

The term may still be useful internally or externally if customer interviews show that buyers immediately understand and value it.

Category validation should ask customers what they call the problem **before** Olympus teaches them what to call it.

# Hypothesis 5: The Buyer Is the CTO / Director / PMO

## Assessment

**Plausible but unvalidated.**

Adjacent products target several different buying centers:

- engineering leaders
- CTOs
- developer productivity leaders
- enterprise IT / knowledge leaders
- operations leaders
- platform teams

This suggests the Olympus buyer cannot be assumed from architecture alone.

Possible user/buyer split:

| Role | Potential value |
|---|---|
| Engineer | trusted project context; fewer stale docs; fewer repeated questions |
| Architect | decision traceability; change impact; architecture continuity |
| Product leader | rationale, scope, product decisions, project history |
| Engineering leader | risk, knowledge health, onboarding, cross-team coherence |
| CTO | portfolio decisions, institutional memory, cross-project dependencies |
| Governance / Compliance | authority, provenance, traceability, evidence |
| PMO / Operations | portfolio continuity and risk, if Olympus extends beyond engineering |

Customer discovery should identify who experiences acute pain and who owns budget. These may be different people.

# Hypothesis 6: Olympus Has a Defensible Differentiator

## Assessment

**Possible, not yet proven.**

The strongest candidate differentiation is not a single feature.

It is the combination of:

## 1. Governed Knowledge Assets

Knowledge carries explicit:

- status
- authority
- ownership
- canonical-source designation
- AI consumption rules
- change impact
- related assets

## 2. Decisions as First-Class Knowledge

Olympus explicitly distinguishes:

- questions
- exploratory concepts
- proposed decisions
- approved decisions
- superseded decisions
- retired decisions

This prevents AI from treating every retrieved fragment as equally authoritative.

## 3. Institutional Experience

Lessons, failures, patterns, risks, and hard-won judgment are intended to survive beyond chats and documents.

## 4. Change Impact Against Governed Meaning

A code or project change could be evaluated against:

- decisions
- standards
- product definitions
- architecture
- lessons
- project dependencies
- cross-project knowledge

rather than merely locating text references.

## 5. Metis-Style Judgment

The system's job is not only retrieval.

It should eventually synthesize:

```text
relevance
+ authority
+ provenance
+ domain lens
+ relationships
+ conflict detection
+ reasoning
```

## 6. Cross-Project Continuity

Olympus began portfolio-wide. A commercial system that retains project boundaries while learning across multiple projects may create differentiation beyond application-specific engineering knowledge tools.

This combination appears less directly represented in the public positioning reviewed in this research.

That is **not proof of product-market fit or technical defensibility**. It is the strongest current hypothesis worth testing.

# Market White Space Hypothesis

A more defensible working thesis is:

> **Existing tools increasingly connect and retrieve project information. Olympus may differentiate by governing what that information means and how AI should reason over it.**

Put another way:

```text
Search products answer:       What information exists?
Engineering intelligence:     What is engineering doing?
Continuous documentation:     Which docs are stale?
Code intelligence:            How does the code work?
Olympus hypothesis:           What does this project know, what is authoritative,
                              what changed, what conflicts, and what should we do next?
```

The final line is still a hypothesis, but it is materially stronger than "AI documentation."

# Recommended Validation Questions

Before MVP implementation, customer interviews should test questions such as:

1. When a major code or product change occurs, how do you determine what else became stale?
2. Where are architectural and product decisions recorded today?
3. How often does your team reopen decisions because rationale cannot be found?
4. Can new team members tell which documentation is authoritative?
5. How do AI coding agents know which internal guidance they should trust?
6. Have AI agents ever acted on outdated or low-authority documentation?
7. How do you capture lessons that should influence future projects?
8. Can leadership identify knowledge risk or decision risk across projects?
9. What happens when code, tickets, docs, and approved decisions disagree?
10. Would solving these problems justify budget beyond existing Jira/GitHub/Confluence/AI tooling?

Do not lead interviews with the term **Project Intelligence**. First learn the customer's own language for the problem.

---

# Recommended MVP Hypothesis

Do not build "Olympus Project Intelligence" broadly.

A sharper experiment is:

> **Given a real project change, can Olympus identify the governed knowledge affected by that change more accurately and usefully than a code/document search workflow?**

Example test:

```text
PR opened or merged
      │
      ▼
Olympus analyzes change
      │
      ▼
Returns affected governed assets
      │
      ├─ documentation
      ├─ approved decisions
      ├─ product requirements
      ├─ architecture guidance
      ├─ lessons / risks
      └─ cross-project dependencies
      │
      ▼
Explains WHY each is affected
      │
      ▼
Separates required review from optional suggestions
      │
      ▼
Human confirms or rejects
```

Success would not be "the AI wrote good docs."

Success would be:

- it found impacts humans would have missed
- it correctly distinguished authority
- it reduced stale knowledge
- reviewers trusted the explanation
- it did not flood users with false positives
- the workflow was valuable enough to repeat

# Implications for ACR-003

This research supports ACR-003's conceptual direction but materially narrows the differentiation claim.

## Supported

- documentation drift is a real product problem
- event-driven human-reviewed agents are feasible
- cross-tool knowledge/context systems are commercially relevant
- project context is increasingly important to AI agents
- leadership pays for engineering intelligence and enterprise context products
- knowledge graphs can support cross-tool reasoning

## Not supported

- Olympus is creating an entirely new category
- nobody is solving the same problem
- documentation stewardship is unique
- a graph is differentiating
- "Project Intelligence" is proven market language
- the CTO/PMO is definitively the buyer
- a 5–8 week MVP is the correct plan

## Stronger surviving hypothesis

> **Olympus may have an opportunity at the intersection of project knowledge, governance, decision traceability, institutional memory, and AI judgment.**

That hypothesis is sufficiently distinct to justify customer discovery and a narrowly scoped experiment.
